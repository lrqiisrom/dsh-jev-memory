# 标注说明

这个目录里是**从你真实历史会话里抽出来的候选句**，用来量出这个插件"记得准不准"。
严格来说，它量的是**你的判断**和插件的判断之间的一致程度——所以判断标准必须一句话说死，且全程只用这一句。

**有三份批次，判断标准完全相同，但各自回答不同的问题：**

| 批次 | 文件 | 行数 | 抽自语料 | 它回答什么 | 优先级 |
|---|---|---|---|---|---|
| round 3 | `round3.csv` | 104 | **编码类**：`projectSDK` + `EchoMind` 的全部候选 | **主指标**：插件该不该记（写入精确率） | **先标它** |
| round 1 | `round1.csv` | 240 | 全部会话 | 学习/办公类的比率、以及筛子有没有误杀 | 其次 |
| round 2 | `round2.csv` | 112 | 只有旧格式日志的 8 个会话 | 旧格式会话与其余有没有系统性差异 | 可选 |

**`round1.csv` 不会被覆盖**，它继续有效；`round3.csv` 是新增的一份，只装编码类。

后两个批次是两次修正的产物：

- **round 2 修的是"读不到"**：抽取器把日志文件名写死成 `session.v3.jsonl.zstd`，而更早的会话写成 `session.jsonl.zstd`，于是**这 8 个会话从未进入过任何样本**（92 条人类消息，占语料约 10%）。
- **round 3 修的是"分错类"**。原来只有一个布尔判断（"这个工作区是不是编码"），它把 `interview` 当成编码线——而 round 1 里 240 行有 221 行来自它，绝大多数是复习问答；同时把 `yakumo-main`、`blarify-main`（讨论自己的项目实现）当成"非编码对照"，期望它们几乎全是 0。按你的判断改过来之后，语料按任务类是这样：

| 任务类 | 工作区 | 通过筛子的候选 |
|---|---|---|
| `coding` | `projectSDK`（这个插件）、`EchoMind…`（客服 agent） | **145** |
| `study` | `interview`、`algorithm`、`yakumo-main`、`blarify-main`（复习 + 写文档） | 807 |
| `office` | `satellite-web`（读专利说明书 .docx、多窗口交互一致性） | 7 |
| `other` | 名单外的新工作区 | 0 |

编码类只有 145 行、学习类 807 行，所以**不可能用一份混合样本同时量这两件事**。round 3 就是把编码类单独拿出来（`coding-signal` 23 条和 `vetoed` 21 条是**普查**，`coding-plain` 抽 60/122）。

### 你标注时发现的两个缺陷（已修，并用你的标注量过代价）

1. **粘贴的转录被当成"你说的话"**。你把整段面试转录贴进过会话，它们以普通用户消息的形式到达，于是里面每一句都像你自己的主张——插件在记面试官问过的问题。语料里这样的句子有 **3,129 句**（转录里每行都以 `你:` 或 `面试官:` 开头，实测只命中这两种标记，不会碰到你自己的第一人称句子）。现在这类句子被 `transcript` 筛子挡下。
2. **只有错误码、没有诊断信息的工具失败没有记忆价值**（你标 `?` 的那几条：`edit 失败：FS_AMBIGUOUS_EDIT`、`cordis_run 失败：未知错误`）。现在这类失败被拒，并记 `tool-failure-no-detail` 到台账；而带原因的那种（`sqlite 写入失败：EDQUOT，磁盘配额用尽…`）仍然会记。

**代价是用你的标注量出来的**：这两条规则拦掉 12 行已标注的句子，其中 9 行你标 0、3 行标 `?`、**标 1 的一行都没有**；"只过筛子"这一臂的精确率因此从 **30% 升到 43%**（编码类 67%→86%，学习类 14%→21%）。

转录行被**排除在 `vetoed` 抽样池之外**：否则从 1,987 行里抽 30 行几乎全是转录，等于花你的时间确认已经确定的事。它们的条数仍然记账（见快照 `vetoes.transcriptExcluded`）。

## 一句话标准

> **换个会话、换一天，这句话还有用吗？**

- **1 = 该长期记住**：它是**你对这个项目的**说法——约定、禁止、取舍及原因、踩过的坑、项目事实。
- **0 = 不该记**：一次性任务指令、寒暄、提问、临时状态、与项目无关的闲聊、以及**没有任何项目特异性的通用知识**（哪怕它本身是对的、很有用）。
- **? = 拿不准**：允许标，但请顺手在 `note` 里写一句为什么——这些是最有价值的数据（说明这条规则有歧义）。
- **留空 = 还没标**。

判断时**不要考虑"插件能不能做到"**，只考虑"该不该"。做不到是插件的问题，不是标准的问题。

方便起见：**标在表头写着 `label` 的那一列**（`round1`/`round2` 里是第 10 列，`round3` 里是第 12 列——因为它多了两列）。不要在行尾追加内容：列是按位置读的，追加到末尾会被当成 `note` 之后的多余字段而**被忽略**（我自己写测试时就踩过这个坑，所以现在有测试盯着它）。

## CSV 的列

| 列 | 含义 |
|---|---|
| `row` | 行号，方便你跟我说"第 37 行我拿不准" |
| `stratum` | 抽样分层（见下表） |
| `task_class` | **只有 `round3` 有**：`coding`/`study`/`office`，报表按它分组 |
| `workspace` | 来自哪个工作区（哪次真实会话） |
| `kind` | `user` = 你本人打的字；`tool-failure` = 工具报的错（正文是"工具名 失败：首行"） |
| `hinted_type` | 规则判定给出的类型提示（`constraint`/`pitfall`/…），空 = 没命中任何类型信号 |
| `signal_score` | **只有 `round3` 有**：抽取器给这句话打的分（0–1），判定层的"规则判定"臂要用它，所以存下来免得复算失真 |
| `veto_reason` | 只有 `vetoed` 层有：被哪条筛子挡下（`task-instruction`/`payload`/`secret`/`noise`/`question`） |
| `seen` | 这句话在历史里去重后出现过几次 |
| `id` | 句子签名，用来回连到台账/记忆库 |
| `text` | **插件当时看到的正文**（可能已被裁剪） |
| `label` | **你填**：1 / 0 / ? |
| `note` | **可选**：拿不准的理由、或任何备注 |

## 四个分层，以及它们各自回答什么问题

| 层 | 含义 | round 3（主指标批） | round 1 | round 2 |
|---|---|---|---|---|
| `coding-signal` | **编码类 + 带类型信号**（像约定/坑/决策） | 23（普查，池子 23） | 120（当时口径不同） | 7 |
| `coding-plain` | **编码类 + 不带信号** | 60（池子 122） | 40 | 40 |
| `study` | 复习/知识问答 | — | 旧文件里混在 `coding-*` 和 `control` 里 | 同左 |
| `office` | 办公/文档 | — | 旧文件里是 `control` | 同左 |
| `vetoed` | **已经被筛子挡掉**的句子（不含转录） | 21（编码类普查） | 30 | 30 |

**主指标（编码写入精确率）用 round 3 算**：编码类里带信号占 **22.2%**、不带信号占 **77.8%**，报表里按这两个池子大小加权，两层各自的小计也单独列（避免用容易的多数派把数字抬上去）。

round 1 / round 2 的 `stratum` 列是旧口径（有 `control` 这类层名），**不影响你标注**：报表会按工作区重新归到上面三个任务类，再分组算比率。旧批次里 `coding-*` 层的行也可能属于 `study` 类，这不是错，是修好的归类在报表里生效。

## 标注顺序（做到哪算哪，随时可以停）

1. **`round3.csv` 的 `coding-signal` 23 行**（价值最高：主指标的分子分母都靠它）
2. **`round3.csv` 的 `vetoed` 21 行**（判"该不该"，**不要被"它已经被挡了"影响**——这是唯一能量出筛子误杀的数据）
3. **`round3.csv` 的 `coding-plain` 60 行**（很快，多数一眼就是 0）
4. `round1.csv` / `round2.csv` 里剩下的，有空再标；它们只影响学习/办公类的比率，不影响主指标。

一次标不完没关系：标注是**按行独立**的，随时停下来都算数。

## 语料快照，以及"为什么重跑不会再浪费你的标注"

`round1.frame.json` / `round2.frame.json` 是和 CSV 一起生成的**语料记账**：读了几个会话日志、各代格式几个、多少条人类消息、各层总体多少、抽了哪些行（存的是行 id 的 sha256 前 16 位，所以这个文件可以进 git，而 CSV 不进）。

写这个文件是因为踩到过一个真实的坑：**第一版抽样器对"语料增长"不稳定**——它把池子排序后用一条 PRNG 流整体洗牌，于是池子里**多一行，整条流就变**，重跑时约一半已抽中的行会被换掉。实测：在真实池规模上（653→666、抽 40 行），旧抽样器换掉 **92.5%** 已抽中的行；改成**逐行哈希排名**（每行的入选只取决于自己）后是 **0%**。

现在的保证是两条，都有测试（`test/harvest.test.ts`）：

- **重跑幂等**：同一份语料、同一个种子，重跑输出的 CSV 逐字节相同；
- **标注不会静默消失**：重抽时标注按句子 id 逐行搬过去；万一一整行已标注的句子不在新样本里，工具**拒绝写出并列出是哪几行**，而不是覆盖掉。真要继续丢，必须显式设 `HARVEST_FORCE=1`。

（本轮修抽样器时有 1 行已标注的句子没能沿用，留在 `round1.orphaned-labels.csv` 里，没有丢。）

## 一行到底是什么（对应关系）

**一行 = 你在某一次真实会话里说过的一句话**，而且是**插件当时看到的样子**（按句切分、必要时裁到 240 字）。

- `workspace` 告诉你它来自哪条项目线（三条编码线 = `ProjectLab/interview`（InterviewMind）、`projectSDK`（这个插件）、`EchoMind…`（客服 agent）；其余（`blarify-main`、`algorithm`）是"复习/刷题"对照）；
- `kind = user` 是**你打的字**；`kind = tool-failure` 是**工具报的错**，正文是"工具名 失败：首行"；
- `id` 只是这句话的指纹（归一化后算的），用来跟台账/记忆库对上，**你不用管它**；
- `hinted_type` 是规则判定给的类型提示，**只是暗示，不影响你怎么判**。它只有 6 个可能值：`constraint` / `pitfall` / `rejected` / `decision` / `procedure` / `preference`（第 7 类 `fact` 规则永远不猜——它是"什么都没命中"时的兜底）。命中即止，优先级就是这个顺序。
  ⚠️ 复算对不上是**正常的**，而且原因有两个：本轮 240 行里有 **128 行带提示**，拿 `text` 重跑文本判定会有 **11 行对不上**——其中 **10 行是 `kind = tool-failure`**（它们的提示来自**失败签名**，例如 `edit 失败：FS_STALE_VERSION` → `pitfall`，本来就不走文本判定），**只有 1 行是截断造成的**（`#39`：提示 `decision`，但正文被裁到 240 字后重算得到 `procedure`）。这不是你眼花，**也不影响怎么标**。
- `seen` 是这句话在历史里出现过几次（去重后只留一行）。

**一行长什么样（示例，不是数据里的真实行）：**

```
row  stratum         workspace                            kind  hinted_type  veto_reason  seen  id          text                               label  note
42   coding-signal   /Users/rom/Documents/projectSDK      user  constraint                3     a1b2c3…     这个项目不要引入 jest，用 node --test   1      项目约定
```

读法：第 42 行是**你在 `projectSDK` 这次会话里打的一句话**，规则判定觉得它像"约束"，`seen=3` 说明这句话在历史里出现过 3 次（去重后只留一行）——于是你判它是"该长期记住"，标 `1`。`id`/`seen`/`hinted_type` 都只是给报表用的，**你只需要决定 `label` 那一格填 1 / 0 / ?**。

**两类会话被处理过**：

- **子代理会话已排除**：委派出去的子会话里，"用户消息"其实是**父代理的提示词**（也就是我写的话），插件自己的规则也拒绝从这里学习，所以不该让你去标。第一版 CSV 没滤掉它们，已经修了（本轮排除 18 个）。
- **旧格式会话已补上**：早期会话的日志文件名没有 `.v3` 后缀，而抽取器原来写死了 v3 的名字，于是这些会话**静默地从未被读到**——8 个会话、92 条人类消息，约占语料 10%（就是 `round2.csv`）。现在按"每个会话只读最新一代"处理：读两代会把迁移过的会话重复计一次，而实测迁移目录里两代确实是同一段对话（都是 207 条人类消息）。

## 两个提醒

- **这份 CSV 里是你真实会话的原句**。默认**不会**提交进 git（已在 `.gitignore` 里排除 `eval/labels/*.csv`）；如果你希望连数据一起版本化，明确说一声，我 `git add -f`。
- 句子是**去重后**的：同一句在历史里出现多次只留一条，`seen` 记录次数。所以 round 1 的 240 行覆盖的是"**976 条去重候选 + 139 条被筛句子（共 1115 行池子）**"的一个分层样本，而不是全部。

## 标完之后

报表工具已经写好了：**`node eval/report.ts`** 会把这三个批次一起读进去，输出 `eval/labels/report.md`，里面有三种判定（只过筛子 / 离线规则判定 / Jev）的精确率与召回率、按任务类和批次的拆分、逐条不一致清单，以及阈值扫描。它做对了几件事，每件都是踩过坑才加的：

- **一句话只算一次**：同一个句子可能同时出现在 `round1.csv` 和 `round3.csv`（标注会跨批次沿用），重复计一次就会把 9 条正例变成 15 条。
- **"只过筛子"同时给两个版本**：一个是**当时**抽这批时的筛子判定（存在 CSV 里），一个是拿**当前**筛子重跑同一句。两者差 10 行——正是你标注指出的转录问题修掉的那些。
- **Jev 跑多次**：模型判定不是确定性的（3 次重复里 20/38 行的分数在变），单次结果是抛硬币。
- **按线上上限分批**：线上每次最多判 6 个候选，超出的降级成规则判定；一次请求塞全部会测一个没人跑的配置。

原计划的"标完我会做什么"剩下这一条没做完：把数据冻结成 baseline（现在已经有语料指纹 `rulesHash`，等标注量够了再做）。



1. 三种判定对照：**只过筛子 / 规则判定 / Jev 判定**，各出精确率、召回率；
2. 按层、按工作区、按类型分别出小计（不许单一项目或单一层主导）；
3. 把**两边不一致的条目逐条列出**（这比平均分有用）；
4. 更新 README 的指标表，并把这次的数据冻结成 baseline（以后改 prompt/阈值都跑它）。

**召回侧**（Hit@K / Recall@K）不在这一轮：它需要"查询 + 正确答案"的标注，得等真实使用里攒出查询来。
