# 借鉴清单：memsearch / 腾讯 / Jev-Mem 论文，我们取什么、不取什么

> 读源码时间 2026-10-02。原文引用见 `docs/memsearch-notes.md`、`docs/industry-memory-notes.md` 的附录，
> 论文见 `docs/jev-mem-paper-notes.md`。每条都标了**我们这边的证据**（数字来自 `eval/labels/report*.md` 与
> `eval/labels/recall-report.md`），没证据的不写进来。

## 一、腾讯的提示词是怎么组装的（可直接对照的模板）

**不是"一个回合"，是"一个窗口"，而且分只读和可抽两层。**

```ts
// MemoryCore/src/core/record/l1-extractor.ts
const maxNewMessages  = options.maxMessagesPerExtraction ?? 10;  // 一次最多抽 10 条新消息
const maxBgMessages   = options.maxBackgroundMessages ?? 5;      // 前面 5 条只读背景

const qualifiedMessages = messages.filter(m => shouldExtractL1(m.content));   // 严格闸门在这一层
const newMessages        = qualifiedMessages.slice(-maxNewMessages);          // 最近 10 条，可抽取
const bgEndIdx           = qualifiedMessages.length - newMessages.length;
const backgroundMessages = bgEndIdx > 0
  ? qualifiedMessages.slice(Math.max(0, bgEndIdx - maxBgMessages), bgEndIdx)  // 再往前 5 条
  : [];
```

提示词骨架（`l1-extraction.ts` 的 `formatExtractionPrompt`）：

```
**输出语言**：根据下方"待提取的新消息"中 user 发言的主导语言书写 …

【上一个情境】：${previousSceneName}          ← 跨批次保持情境连续

【背景对话】（仅供理解上下文推断关系/时间，严禁从中提取记忆）：
[id] [role] [timestamp]: content              ← 每条都带 id / 角色 / 时间
…

【待提取的新消息】（务必结合 timestamp 推算时间，只从这里提取记忆！）：
[id] [role] [timestamp]: content
```

一次调用同时产出两样东西：**情境切分**（每条消息属于哪个情境，输出里带消息范围）和**记忆抽取**
（类型/优先级/正文/时间元数据）。系统提示词里那条"从背景消息严禁新增提取记忆"是这套设计的关键——
**给上下文，但不开新的记忆面**。

三层设计值得整体照抄：

| 层 | 做法 | 出处 |
|---|---|---|
| **L0 采集** | **故意宽松**——只丢空消息、框架噪声、斜杠命令；"保留尽可能多的用户输入" | `utils/sanitize.ts` `shouldCaptureL0` |
| **L0 钩子** | 只写 L0 + 通知，**不抽取**；由 pipeline manager 决定何时抽（默认每 5 个会话或空闲 60s） | `hooks/auto-capture.ts` |
| **L1 抽取** | **严格闸门 + 窗口 + 批量**（上面那段），异步跑 | `record/l1-extractor.ts` |

顺带两条细节：

- `stripCodeBlocks()` **只作用于 `role=assistant` 的消息**（注释明说 "user messages and recall queries are NOT affected"）——**用户消息里的粘贴块不受任何处理**，这正是我们担心的那个缺口，他们没有堵。
- 抽取出 0 条时会打一行可 grep 的 `l1-empty reason=<label>`，注释写着"a silent 0-count run should never happen again"。

## 二、借什么（按价值排序，每条附我们的证据）

### 1. 两层存储：原文全留，闸门只决定"注入资格"

**腾讯**：L0 全留、L1 才严筛。**论文**：不在摄入时做 store-or-discard，"此刻看着没用的信息，将来某天可能正需要，丢了就找不回来"。

**我们的证据**：写入侧一道硬闸门决定生死，结果是**该记覆盖率 50%**（18 条要求只写 9 条），
另有 122 条标 0 的行只存在于标注 CSV 里——**插件自己已经把它们扔了**。
如果 L0 全留，将来改问法/改阈值**可以拿同一个会话重新抽一遍，不用重新采集**。

代价要说清：留全 = 存储和隐私面变大，所以**必须默认不注入**，只在 `memory_search` 里能查到。

### 2. 只读背景窗口

**腾讯**：最近 10 条可抽 + 前 5 条只读，提示词明写"严禁从背景消息中新增提取记忆"。

**我们的证据**：17 行 note 说"上下文并不完整／应该还有下文"，你因此只能标 `?`。
根因是我们逐句处理、没有窗口概念。**给上下文但不扩大记忆面**正是缺的那块。

### 3. 角色写进喂给模型的内容

**腾讯**：每条渲染成 `[id] [role] [timestamp]: content`，并配一条"AI/Agent 输出处理"规则。

**我们的证据**：我们把**单句**（不带说话人、不带前后文）送去判定；30 行 note 说"这是模型的输出"，
**0 行标 1，而今天仍有 24 行会被放行**。没有角色信息，判定层无从判断。

### 4. "抽取出 0 条"要记账

**腾讯**：`l1-empty reason=<label>`，一行可 grep。

**我们的证据**：我们有 `kind:"skip"` 带 reason，但**"这一轮一条都没抽出来"没有专门的记录**。
这是最该告警的情形，却是目前唯一静默的情形。顺手就能补。

### 5. RRF 只当锚点，最终排序要重排（论文）

**论文**：向量 + 词面两路用 RRF（κ=60）融合做**锚点**，之后由控制器逐候选重排（式 23）。

**我们的证据**：我测出 RRF 当**最终**排序时 0.83，不如纯 embedding 的 0.90，所以否掉了。
**我的实验比论文少一层**——它有重排阶段，我没有。这条修正已写进论文笔记。

### 6. 多标签类型分数（论文）

**论文**：`t(v) = (episodic, semantic, procedural, preference)`，四个重叠分数，"标注节点而不是归到单一互斥类别"。

**我们**：单标签（constraint / pitfall / decision / fact）。一条"既像坑又像决策"的句子会丢掉一半信息，
而类型直接决定注入配额（硬约束 4 / 坑 3 / 决策 2）。

## 三、不借什么（理由要充分，不然会被"顺手补上"）

### 1. 不把记忆内容变成"这一回合发生了什么"（memsearch）

它的提示词写得很清楚：你是**第三人称记录员**、**外部观察者**，输出"第一条 bullet 是 User 想要什么，
其余是做了什么/发现/决定了什么"。**它的记忆单位是会话笔记。**

**我们不是。** 我们存的是"用户自己的长期要求"，而且会作为**约束**注入到以后每个会话。
同一段粘贴块，在它那里只是让笔记长一点，在我们这里是**假约束**。这也是你的标注标准里
"模型写的 = 0"那一条不肯放弃的原因。

### 2. 不让模型写记忆正文（腾讯的 `merged_content` 恰恰相反）

腾讯的合并/更新由模型写出新正文（`l1-dedup` 的 `merged_content`），理由是它要支持跨类型合并。
**我们的纪律是"模型不写正文"**——正文永远是切出来的原文，这是"证据层"能成立的前提，
也是台账能逐条追责的基础。要合并也只能**拼接/选段**，不能重写。

### 3. 不照抄"靠规则 7 解决粘贴问题"

腾讯的规则 7（不要把 AI 的建议当成团队事实，只有人类采纳才算）管的是 **role=assistant 的消息**。
用户把模型输出**粘进自己的消息**后 role 就是 user，**那条规则不会触发**；整个文件里没有一条
针对"用户消息内部的粘贴区间"的规则（grep `引用|他人的|第三方|转述|复制` 只命中 work_artifact 定义里的一处）。
memsearch 则根本不需要这条规则。

**所以这是真空地带，只能我们自己补**——而且对我们比对它们严重。

## 四、我们还需要做什么（按价值排序）

| # | 事项 | 证据 | 验收方式 |
|---|---|---|---|
| **P0** | **"谁说的"检测**：拿同一会话里更早的 assistant 消息做回显比对 | 30 行 note 说"这是模型的输出"，**0 行标 1**；今天仍放行 24 行；正则已证明无效（最好的候选信号只命中 4/30） | 在这 30 行上量：救回多少、误杀多少（必须 0 误杀） |
| **P1** | **写入侧改两层**：原文全留（不注入），闸门只决定注入资格 | 该记覆盖率 50%；122 条标 0 的行已被插件丢弃，无法重新抽取 | 冻结一份 L0 快照；改阈值后能重跑同一批而不用重采会话 |
| **P2** | **自动注入加查询感知** | 注入覆盖率 **2/36 = 6%**，因为它按"重要度 + 衰减 + 配额"挑，完全不看查询 | 同一批 36 探针，覆盖率上升且注入 token 不涨 |
| **P3** | **异步抽取通道** | 写入跑在 `agent/turn-stopping`，预算 2500ms，一次 LLM 调用即超时（腾讯正是靠异步解决） | 后台队列可批量、可重试、可观测积压 |
| **P4** | **多相关标注 + 多类型探针** | 现在相关性是单目标口径；`recall1.csv` 里非目标行的 `label` 还空着 | 标完后重算"注入精确率"，看单目标假设罚错了多少 |
| **P5** | **跨类型复验新问法** | 新问法 AUC 0.75 **只在编码类**；学习类 21 行 AUC **0.31**（3 条正例，但三跑方向一致） | 抽一批跨类型数据，按类型分别算 AUC |
| **P6** | **"抽取出 0 条"记账** | 目前唯一静默的失败情形 | 台账出现 `kind:"extract-empty"` 并带 reason |
| **P7** | **多标签类型分数** | 单标签丢掉"既是坑又是决策"的信息，而类型决定注入配额 | 类型分数改为 4 个重叠分，配额按主类型仍可用 |

**P0 和 P1 是同一件事的两半**：P1 让被丢弃的内容留在库里，P0 决定留在库里的哪一段算"用户说的"。
先做 P0（它决定 P1 的存储格式里要不要带 attribution），再做 P1。
