# 读取侧基线：怎么量"记忆用不用得上"

## 为什么现在必须开始

写入侧回答的是**记不记得住**：一句该记的话，插件有没有写下来。它现在的基线是 `eval/labels/baseline.json`（round5，140 行已定）。

读取侧回答的是**用不用得上**：一个新会话里你问了一件事，之前记下的那条有没有被想起来、有没有进上下文。**这一侧一个数字都没有**，而"长期记忆"这个名字说的是读取侧。

已经能看出来的一个数字说明这件事有多要紧：召回注入的预算是有限的（现在 1 条约 60 tokens），而写入侧"只过筛子"那一臂会放行 93/140。如果读取侧不做选择，要么注入被塞满噪音，要么真正有用的那几条被挤掉。**写入侧的精确率 24% 意味着读取侧的输入里有四分之三是垃圾**——所以读取侧同时要承担"选对"和"挡住写入侧漏过来的垃圾"两件事。

## 量什么

| 指标 | 一句话定义 | 为什么需要它 |
|---|---|---|
| **Hit@K** | 对每个查询，前 K 条里**只要有一条第 1 类相关**就算命中；命中数 ÷ 查询数 | 最宽松也最贴近体感：我要的东西在不在 |
| **Recall@K** | 对每个查询，前 K 条里的相关条数 ÷ 该查询**全部**相关条数，再取平均 | 该想起 3 条只想起 1 条，Hit@K 看不出来 |
| **MRR** | 第一条相关的排在第几位，取倒数再平均 | 第 1 条就命中 vs 第 5 条才命中，体感差很多 |
| **注入精确率** | 注进上下文的那 K 条里，相关占比 | 对应写入侧的"写对率"：脏东西有没有被喂进提示 |
| **注入 token** | 台账 `kind:"recall"` 的 `tokens`（已有） | 命中率不能靠无限注入换 |
| **漏掉的原因** | 没命中时分类：`没写进记忆` / `写进了但没召回` / `召回了但被挤出预算` | 决定该修写入侧还是读取侧 |

最后一行是这个设计里最重要的：**同一个"没命中"有三个完全不同的成因**，不分开就只能瞎改。

## 数据从哪来（三种查询，成本从低到高）

### A. 从已标注的"该记"句子反向生成探针（零人工，立刻能做）

round5 里有 18 条你标"该记"的句子，它们已经被证明有长期价值。对每一条生成 1~3 个**查询**，语义上应该把它想起来，但**不含它的原词**：

| 记忆 | 生成的查询（示意） |
|---|---|
| `语言不要选 Java` | "这个插件的实现语言有什么限制？" |
| `git 仓库链接也带上去，简历里不要出现 memory.json 这种文件名` | "写简历的时候对文件名有什么要求？" |

生成方式：用宿主的 `llm` 服务（和规范化走同一条路，已验证可用）。**必须检查生成结果和原句的词汇重合度**，重合太高说明是抄词不是查询——那种查询任何检索都能命中，量出来的数字没有意义。沿用规范化那套闸门思路：设一个重合度上限。

优点：今天就能出一版数字。缺点：**这是我自己出的题**，可能有偏；而且它只测"已知该记的东西能不能被想起来"，不测"该不该想起来"。

### B. 从真实会话里抽查询 + 你标"应该想起哪几条"（人工，最可信）

从会话里抽**真实的用户消息作为查询**（不是生成的），然后把**当时库里已有的记忆**全部列出来给你，你标：

- `1` = 这条查询下，这条记忆应该被注入
- `0` = 不该
- `?` = 拿不准

这是唯一能测"该不该想起来"的方式，因为它带着真实的意图和语境。成本：每条查询要标 10~20 条候选，**比写入侧贵得多**（写入侧一行标一句，这里一行要标一批）。

降本做法：**先只标 top-5**（读取侧实际会注入的那几条——K 之外标了也没用，除非要算 Recall@K 的分母）。配合 A 一起做：A 出数字，B 抽 10~20 条查询校验 A 有没有偏。

### C. 会话内的自然对照（零标注，只能做定性）

同一个会话里，你第 5 轮说过的事，第 30 轮又提了一次——**第 30 轮就是一次真实的召回失败**。这类样本可以自动挖出来（同一签名/同一主题的重复出现），不需要标注，但它只能告诉你"漏了什么"，不能算 Recall@K（没有分母）。

**建议路线：先 A（今天出数）→ 再用 B 抽 10~20 条校验 → C 作为持续的回归信号。**

## 文件格式

### `eval/labels/recall1.csv`（查询标注）

沿用写入侧的习惯：一行一个 (查询, 记忆) 对，你和现在一样只填 `label` 和 `note`。

| 列 | 谁填 | 含义 |
|---|---|---|
| `query_id` | 工具 | 查询的稳定 id（`signatureOf(查询原文)`） |
| `query` | 工具 | 查询原文 |
| `query_source` | 工具 | `derived`（从记忆反向生成）/ `session`（真实用户消息）/ `repeat`（同一会话里重复出现） |
| `memory_id` | 工具 | 记忆的 id（写入侧那个 id，两边能对上） |
| `memory_text` | 工具 | 记忆原文 |
| `rank` | 工具 | **当时的检索把它排在第几**（0 = 没进候选） |
| `score` | 工具 | 当时的检索分数，便于以后看排序变化 |
| `label` | **你** | `1` = 这条查询下应该想起它；`0` = 不该；`?` = 拿不准 |
| `note` | **你** | 为什么 |

关键点：`rank` 和 `score` 是**工具跑出来的、冻结在文件里**的。这样以后改了检索算法，只要重新跑一遍就能对比——**同一份人工标注可以反复用**，这是写入侧那套能一直用的原因，读取侧照搬。

### `eval/labels/baseline-recall.json`（基线）

和 `baseline.json` 同一个机制：记录数据集（哪个 recall 文件、多少查询、多少对）、检索配置（K、配额、加权、是否用 embedding）、指标（Hit@K / Recall@K / MRR / 注入精确率 / token）、以及**当时的排序结果指纹**。

报告里同样加一节"与基线对比"，只在查询集合一致时出现。

## 怎么跑

```
eval/harvest-queries.ts    抽查询候选（A/B/C 三源），写出 recall1.csv 的骨架（label 留空）
eval/recall-report.ts      读 recall1.csv，跑检索，算 Hit@K / Recall@K / MRR / 注入精确率 / token
                           REPORT_BASELINE_RECALL_OUT=... 冻结基线
```

`recall-report.ts` 需要一份**记忆库快照**才能离线跑。两个选择：

1. **用当前真实库**（`memory.json`）：最真实，但库在变，不同时间的数字不可比；
2. **冻结一份快照**（`.scratch` 下，或标注文件里把 `memory_text` 写全）：可比、可复现。

**取 2**：`memory_text` 已经在 CSV 里了，报告直接用它建一个内存库，不依赖真实库的状态。这样同一份标注永远算出同一个数，除了检索算法本身。

## 与写入侧的关系（别混）

- 写入侧的 `该记覆盖率` = 你标该记的句子里，插件写了几条。
- 读取侧的 `Recall@K` = 某个查询下应该想起的 N 条里，前 K 条里有几条。
- **两者相乘才是端到端的漏记率**：一条要求被记下的概率 × 需要时被想起来的概率。现在只测了前一半。

## 第一步具体做什么（不需要你写代码）

1. 我实现 `harvest-queries.ts`（先只做 A 源），从 round5 那 18 条"该记"生成查询，**写出骨架 CSV**：每行一个 (查询, 记忆) 对，`label` 留空。
2. 你只需要做一件事：**对每个查询，看 top-5 里哪几条应该被注入**，填 `1`/`0`/`?`。查询数量控制在你标得完的范围（建议 15~20 个查询）。
3. 跑 `eval/recall-report.ts`，冻结第一个读取侧基线。

预估工作量：18 条记忆 → 约 20 个查询 → 每个看 5 条候选 = 约 100 个判断，**和你标 round5 的 147 行差不多量级**。
