## 第一版跑出来的结果

**数据集**：36 个探针（18 条你标"该记"的记忆 × 2 种问法），库 94 条（18 条真记忆 + 76 条闸门会写进去的垃圾，垃圾占 81%）。

**两种问法**：**近** = 换个会话再问一次，可以复用记忆里的词（词汇重合度 0.81）；**远** = 同一件事换个说法，不许用记忆里的关键名词（重合度 0.17）。

| 检索方式 | 近+远 Hit@1 | 近+远 MRR | MRR（远问法） | 完全找不到 | 标识符 Hit@1 | 标识符 MRR |
|---|---|---|---|---|---|---|
| 旧版子串匹配 | 22% | 0.23 | 0.06 | 27 / 36 | 95% | 0.97 |
| embedding（embedding-3，512 维） | 86% | 0.90 | 0.83 | 0 / 36 | **0%** | **0.00** |
| 纯 BM25（改到一半时的样子） | 67% | 0.71 | 0.46 | 2 / 36 | **0%** | 0.31 |
| BM25 + 名字精确命中加成（**现在上线的**） | **67%** | **0.71** | 0.46 | 2 / 36 | **100%** | **1.00** |
| BM25 + embedding 归一化相加 | 67% | 0.74 | 0.50 | 0 / 36 | 0% | 0.31 |
| RRF 融合（按名次） | 78% | 0.83 | 0.68 | 0 / 36 | 0% | 0.31 |

**自动注入（不看问题的那条路）覆盖率：2 / 36（6%）**，每次注入 641 token（预算 600）。

三个结论：

1. **子串匹配根本不该用来检索**：远问法 18 条里 17 条什么都返回不了。换成 BM25（项目里本来就有，一直在给冲突排序用）是零新增依赖的改动，MRR 0.23 → 0.71。
2. **embedding 明显更强，而且不是"各有胜负"**：逐条比过——Hit@5 内两边都中 27 条，**只有 embedding 中的 7 条，只有 BM25 中的 0 条**。所以是换掉而不是融合。
3. **融合反而更差**。朴素归一化相加只有 0.74（比 embedding 单独用低 0.16），因为 BM25 对它的第一名永远给 1.0 分，一个自信但错误的词面命中会压过语义命中；RRF 按名次融合只找回一部分（0.83）。所以实现成**一个 ranking 模式**（`searchRanking: lexical | embedding`），不是混合。

**诚实说明**：这两组探针都是我自己出的题（一组用模型造、一组机械生成），不是真人查询日志；而且**"embedding 在散文上严格占优"只对散文成立**——补上标识符那一组（22 个探针）之后，embedding 在那里的 MRR 是 **0.00**，纯 BM25 是 0.31，旧子串匹配反而是 0.97。所以"换掉子串匹配"这个决定在标识符这一类上是我先弄坏了、再补回来的：现在靠**名字精确命中加成**把标识符做到 1.00，同时散文的分毫未动。

## 为什么现在必须开始

写入侧回答的是**记不记得住**：一句该记的话，插件有没有写下来。它现在的基线是 `eval/labels/baseline.json`（round5，140 行已定）。

读取侧回答的是**用不用得上**：一个新会话里你问了一件事，之前记下的那条有没有被想起来、有没有进上下文。**这一侧一个数字都没有**，而"长期记忆"这个名字说的是读取侧。

已经能看出来的一个数字说明这件事有多要紧：召回注入的预算是有限的（现在 1 条约 60 tokens），而写入侧"只过筛子"那一臂会放行 93/140。如果读取侧不做选择，要么注入被塞满噪音，要么真正有用的那几条被挤掉。**写入侧的精确率 24% 意味着读取侧的输入里有四分之三是垃圾**——所以读取侧同时要承担"选对"和"挡住写入侧漏过来的垃圾"两件事。

## 量什么

| 指标 | 一句话定义 | 为什么需要它 |
|---|---|---|
| **Hit@K** | 对每个查询，前 K 条里**只要有一条第 1 类相关**就算命中；命中数 ÷ 查询数 | 最宽松也最贴近体感：我要的东西在不在 |
| **Recall@K** | 对每个查询，前 K 条里的相关条数 ÷ 该查询**全部**相关条数，再取平均 | 该想起 3 条只想起 1 条，Hit@K 看不出来 |
| **MRR** | 第一条相关的排在第几位，取倒数再平均 | 第 1 条就命中 vs 第 5 条才命中，体感差很多 |
| **注入精确率** | 注进上下文的那 K 条里，相关占比 | 对应写入侧的"写对率"：脏东西有没有被喂进提示 |
| **注入 token** | 台账 `kind:"recall"` 的 `tokens`（已有） | 命中率不能靠无限注入换 |
| **漏掉的原因** | 没命中时分类：`没写进记忆` / `写进了但没召回` / `召回了但被挤出预算` | 决定该修写入侧还是读取侧 |

最后一行是这个设计里最重要的：**同一个"没命中"有三个完全不同的成因**，不分开就只能瞎改。

## 数据从哪来（三种查询，成本从低到高）

### A. 从已标注的"该记"句子反向生成探针（零人工，立刻能做）

round5 里有 18 条你标"该记"的句子，它们已经被证明有长期价值。对每一条生成 1~3 个**查询**，语义上应该把它想起来，但**不含它的原词**：

| 记忆 | 生成的查询（示意） |
|---|---|
| `语言不要选 Java` | "这个插件的实现语言有什么限制？" |
| `git 仓库链接也带上去，简历里不要出现 memory.json 这种文件名` | "写简历的时候对文件名有什么要求？" |

生成方式：用宿主的 `llm` 服务（和规范化走同一条路，已验证可用）。**必须检查生成结果和原句的词汇重合度**，重合太高说明是抄词不是查询——那种查询任何检索都能命中，量出来的数字没有意义。沿用规范化那套闸门思路：设一个重合度上限。

优点：今天就能出一版数字。缺点：**这是我自己出的题**，可能有偏；而且它只测"已知该记的东西能不能被想起来"，不测"该不该想起来"。

### B. 从真实会话里抽查询 + 你标"应该想起哪几条"（人工，最可信）

从会话里抽**真实的用户消息作为查询**（不是生成的），然后把**当时库里已有的记忆**全部列出来给你，你标：

- `1` = 这条查询下，这条记忆应该被注入
- `0` = 不该
- `?` = 拿不准

这是唯一能测"该不该想起来"的方式，因为它带着真实的意图和语境。成本：每条查询要标 10~20 条候选，**比写入侧贵得多**（写入侧一行标一句，这里一行要标一批）。

降本做法：**先只标 top-5**（读取侧实际会注入的那几条——K 之外标了也没用，除非要算 Recall@K 的分母）。配合 A 一起做：A 出数字，B 抽 10~20 条查询校验 A 有没有偏。

### C. 会话内的自然对照（零标注，只能做定性）

同一个会话里，你第 5 轮说过的事，第 30 轮又提了一次——**第 30 轮就是一次真实的召回失败**。这类样本可以自动挖出来（同一签名/同一主题的重复出现），不需要标注，但它只能告诉你"漏了什么"，不能算 Recall@K（没有分母）。

**建议路线：先 A（今天出数）→ 再用 B 抽 10~20 条校验 → C 作为持续的回归信号。**

## 文件格式

### `eval/labels/recall1.csv`（查询标注）

沿用写入侧的习惯：一行一个 (查询, 记忆) 对，你和现在一样只填 `label` 和 `note`。

| 列 | 谁填 | 含义 |
|---|---|---|
| `query_id` | 工具 | 查询的稳定 id（`signatureOf(查询原文)`） |
| `query` | 工具 | 查询原文 |
| `query_source` | 工具 | `derived`（从记忆反向生成）/ `session`（真实用户消息）/ `repeat`（同一会话里重复出现） |
| `memory_id` | 工具 | 记忆的 id（写入侧那个 id，两边能对上） |
| `memory_text` | 工具 | 记忆原文 |
| `rank` | 工具 | **当时的检索把它排在第几**（0 = 没进候选） |
| `score` | 工具 | 当时的检索分数，便于以后看排序变化 |
| `label` | **你** | `1` = 这条查询下应该想起它；`0` = 不该；`?` = 拿不准 |
| `note` | **你** | 为什么 |

关键点：`rank` 和 `score` 是**工具跑出来的、冻结在文件里**的。这样以后改了检索算法，只要重新跑一遍就能对比——**同一份人工标注可以反复用**，这是写入侧那套能一直用的原因，读取侧照搬。

### `eval/labels/baseline-recall.json`（基线）

和 `baseline.json` 同一个机制：记录数据集（哪个 recall 文件、多少查询、多少对）、检索配置（K、配额、加权、是否用 embedding）、指标（Hit@K / Recall@K / MRR / 注入精确率 / token）、以及**当时的排序结果指纹**。

报告里同样加一节"与基线对比"，只在查询集合一致时出现。

## 怎么跑

```bash
# 造探针（每个记忆 2 个，会调模型；探针会缓存到 recall1.probes.json，重跑不再花钱）
QUESTIONS_LIMIT=18 node eval/harvest-queries.ts
# 换检索算法后重建候选表和 rank/score（复用缓存探针，不花钱）
node eval/harvest-queries.ts
# 算指标；加环境变量则冻结基线
RECALL_BASELINE_OUT=eval/labels/baseline-recall.json node eval/recall-report.ts
```

写入侧和读取侧的评测是分开的两条命令、两份基线：`node eval/report.ts`（写入）与
`node eval/recall-report.ts`（读取）。同一个词在两边的含义不同，报告里各自写明了。

`recall-report.ts` 需要一份**记忆库快照**才能离线跑。两个选择：

1. **用当前真实库**（`memory.json`）：最真实，但库在变，不同时间的数字不可比；
2. **冻结一份快照**（`.scratch` 下，或标注文件里把 `memory_text` 写全）：可比、可复现。

**取 2**：`memory_text` 已经在 CSV 里了，报告直接用它建一个内存库，不依赖真实库的状态。这样同一份标注永远算出同一个数，除了检索算法本身。

## 与写入侧的关系（别混）

- 写入侧的 `该记覆盖率` = 你标该记的句子里，插件写了几条。
- 读取侧的 `Recall@K` = 某个查询下应该想起的 N 条里，前 K 条里有几条。
- **两者相乘才是端到端的漏记率**：一条要求被记下的概率 × 需要时被想起来的概率。现在只测了前一半。

## 第二版：让注入看一眼当前对话（2026-10-03）

第一版最大的缺口是**自动注入覆盖率 2/36（6%）**——注入完全不看问题，按"重要度 ×0.85 + 时间衰减 ×0.15 + 类型配额"塞固定几条。
改成把**这个人最近几条消息**当查询，和重要度做加权混合（`selectMemories` 的 `query` / `relevanceWeight`），
用同 36 个探针扫权重（每个探针用它自己的查询跑一次注入，配额与预算不变）：

| 相关性权重 | 覆盖率 | 平均 token | 注入里真记忆占比 |
|---|---|---|---|
| 0（第一版的排序） | 0 / 36（0%） | 594 | — |
| 0.2 | 15 / 36（42%） | 587 | 18% |
| 0.35 | 16 / 36（44%） | 590 | 22% |
| 0.5 | 16 / 36（44%） | 591 | 30% |
| 0.65 | 17 / 36（47%） | 591 | 38% |
| **0.8（上线默认）** | **17 / 36（47%）** | 592 | **42%** |
| 1 | 16 / 36（44%） | 585 | 39% |

两列在 0.8 同时到顶，**而且不是拿一个换另一个**——这值得说一句，因为"按相关度注入"通常的反对意见是
"会把只要沾一点词的东西塞满预算"。这里相反：旧排序是被**重要度**塞满的，而库里"看起来重要"的记录
大多是写入侧的假阳性（冻结语料里 94 条有 76 条是）。权重不取 1.0 的理由是**探针测不到的那件事**：
这一轮刚写进来、对话里还没提过的记忆，在全权重下相关度是 0，只有重要度能把它带进来——这一点按设计写下来，
不当成测量结果。

**顺带修掉一个预算 bug**：注入块的 token 数只算了记忆行，没算标题和撤销提示，实测是 **641 token 对 600 预算**——
插件自己报了个预算又超了它。现在固定开销先扣，代价是旧排序的覆盖率从 2/36 变成 **0/36**（那两条正是第 5 条），
而新排序在 592 token 内拿到 17/36。

### 剩下的缺口在哪：三道闸门的漏斗

覆盖率到 47% 就不再涨，原因不是排序。把"在库里"到"进了提示"之间的三道闸门分开量：

| 卡在哪一道 | 条数 | 说明 |
|---|---|---|
| **被注入了** | 17 | — |
| **类型过滤（`types` 白名单）** | **16** | 与排序无关：这些目标被标成 `fact`，这类记忆再相关也进不了提示 |
| 类型配额（4/3/2）挤掉 | 0 | 排序对了，名额也够 |
| token 预算挤掉 | 3 | 排序对了，600 装不下 |
| 相关性没排进 | **0** | **检索/排序已经不是瓶颈** |

也就是说：**读取侧的排序现在满分，天花板是写入侧那座类型白名单**。这和写入侧那条"21 条正例里 8 条死在
类型白名单上"是同一座墙的两面——一句话如果没有类型关键词，写入侧判它是 `fact` 并拒写，所以线上库里
**一条 `fact` 都没有**（核对过线上 `memory.json`：16 条全是 constraint / decision / pitfall）。
所以这 16 条不是读取侧能修的，要先决定**写入侧白名单要不要放宽**——那是个有标注依据的用户决定，
不在这一版里自己改。

**预算这个旋钮也量了，结论是别动它**（否定结果）：

| token 预算 | 覆盖率 | 每轮实际用掉 |
|---|---|---|
| 600（今天） | 17 / 36（47%） | 592 |
| 1200 | 18 / 36（50%） | 1173 |
| 2000 | 18 / 36（50%） | 1569 |

每轮多花约 580 token 只换 **1 个探针**。所以剩下的缺口不在预算——在类型白名单。

**可复跑**：`node eval/recall-report.ts` 会重算上面三张表和漏斗；冻结进 `eval/labels/baseline-recall.json` 的
`injection.sweep`。

### 刚写进来的记忆会不会被漏掉（2026-10-03，模拟测量）

这一项（"避免刚记的东西检索不到"）冻结语料**测不到**：它给每条记录的 `createdAt` 都是 0。
所以做了一组**明确标注为模拟**的探针：给每个探针额外追加一条"刚写的"记录（时间戳 = 现在），
追加的东西在两次运行里分别是**一条真记忆**和**一条假阳性**，再看它有没有被注入。

两种机制，一个问题——**硬保证**（预留槽位，不管相关度最刚写的一定有位置，代价是挤掉排名最低的那条）
还是**软竞争**（分数加一点，弱相关会被它超过，强相关不会）：

| 机制 | 刚写的真记忆被注入 | 刚写的假阳性被注入 | 覆盖率 | 每轮 token |
|---|---|---|---|---|
| 0（今天） | 9 / 36 | 7 / 36 | 17 / 36 | 591 |
| 预留槽位 1 | 29 / 36 | 34 / 36 | **16 / 36** | 491 |
| 预留槽位 2 | 28 / 36 | 29 / 36 | **11 / 36** | 497 |
| 新近加成 0.1 | 21 / 36 | 24 / 36 | 17 / 36 | 592 |
| 新近加成 0.2 | 25 / 36 | 26 / 36 | 17 / 36 | 591 |
| **新近加成 0.4（上线）** | **32 / 36** | 32 / 36 | **17 / 36** | 591 |
| 新近加成 0.6 | 36 / 36 | 35 / 36 | 16 / 36 | 591 |

**软竞争严格优于硬保证**：0.4 就到 32/36，而且覆盖率**一点没掉**；预留槽位到 29/36 就要拿覆盖率换
（17→16，两个槽位 17→11，因为它挤掉的正是排名最低的那条——在探针里那常常就是探针自己的目标）。
0.6 能到 36/36，但覆盖率掉 1，说明它已经开始滑回"硬保证"那个区间，所以**不取**。

**代价那一列两种机制一样高**（32/36），因为它们都只看时间、不看内容——而写入侧精确率 24%，
"刚写的"有四分之三的概率是垃圾。这个代价不是机制能解决的，是写入侧的事。

**两个测量错误记在这里，因为都很容易再犯**：
1. 第一版的"现在"写成了固定时间戳 `1_700_000_000_000`（2023 年），而 `selectMemories` 内部默认
   用 `Date.now()` 算年龄——那条"刚写的"记录因此老了 1000 天，加成项恒为 0，**连续三轮扫描全是同一组数字**。
2. 第一版用 `positives.find(...)` 挑"刚写的真记忆"，它对每个探针返回**同一条**记录；那条恰好是 `fact` 类型时
   （不在注入白名单里）整张表又变成在量类型过滤。**改成轮转挑选 + 只挑有资格被注入的**之后数字才有意义。

### 注入块把每条记忆印了两遍（2026-10-03）

看注入块的真实样子时发现的，而且是**最便宜的一次覆盖率提升**：

```
- [constraint] 语言不要选 java：dsh 的 java native 插件方案不考虑 (语言不要选 java：dsh 的 java native 插件方案不考虑, 2026-09-28)
```

括号里的 id 就是这句话本身（`id = signatureOf(text)`，只把数字和引号折成 `<n>`/`<str>`）。
**线上 16 条记录，16 条的 id 都等于自己的签名**——所以每一行都在打印同一段文字两遍，
而这块本来就超预算（641 token 对 600）。

改成"id 与原文相同时不印 id"（`recall.omitRedundantId`，默认开；`memory_forget` 本来就支持按 `query` 删，
所以没有东西变得不可撤销），同一批预算下的效果：

| | 注入条数 | 平均 token | 覆盖率 | token 预算卡掉的探针 |
|---|---|---|---|---|
| 印重复的 id | 4.4 | 592 | 17 / 36 | 3 |
| **不印（现在）** | **6.5** | 591 | **18 / 36** | **1** |

**同样的 token 多装了 48% 的记忆**，覆盖率 +1，漏斗里"预算卡掉"从 3 降到 1。
现在漏斗里剩下的是类型白名单 16 条 + 配额 1 条 + 预算 1 条——**排序依然是 0**。

### 检索方式的全表（2026-10-03，含两次否定结果）

到这里检索这一侧的量已经完整了，四种做法 + 两个否决：

| 做法 | 全部 MRR | 近问法 | 远问法 | 标识符 MRR |
|---|---|---|---|---|
| 纯 BM25（无名字加成） | 0.71 | 0.97 | 0.46 | 0.31 |
| **词面检索（默认：BM25 + 名字精确命中加成）** | 0.71 | 0.97 | 0.46 | **1.00** |
| 伪相关反馈（PRF，前 3 条共同词） | 0.71 | 0.97 | **0.45** | — |
| 伪相关反馈（PRF，前 1 条） | 0.71 | 0.97 | **0.44** | — |
| RRF 融合（用上线的词面检索）+ 名字钉住 | 0.78 | **0.88** | 0.68 | 0.98 |
| embedding（512 维） | 0.90 | 0.97 | 0.83 | **0.00** |
| **embedding + 名字钉住（名字出现在 ≤2 条记忆里）** | **0.92** | **1.00** | 0.83 | **0.98** |

三个结论：

1. **PRF 没用**（否定结果，两次都是）：远问法 0.46 → 0.45 / 0.44，一个都没往前挪。
   原理上讲得通——远问法的困难是**词汇不重合**，而前几条命中里"共同的词"来自**可能错的文档**，
   扩展只会加固原来的判断。顺带记一个自己犯的测量错误：第一版给 topK=1 的变体写了 `count >= 2` 的过滤，
   这在只有一条文档时永远不成立，于是"top 1"那行量的其实是基线。

2. **融合也没用，而且是负的**（否定结果）：把**上线的**词面检索和 embedding 按名次融合，
   比拿纯 BM25 去融合更差（全部 MRR 0.78 对 0.83），近问法还从 0.97 掉到 0.88。
   原因是 `searchMemories` 只返回分数为正的记录，名次表很短，而 RRF 的 1/(60+rank) 很平，
   顶上几条就变成了掷硬币。**要修的是那个洞，不是融合。**

3. **名字钉住（只钉"出现在 ≤2 条记忆里"的名字）是唯一活下来的改动**：identifier 从 0.00 → 0.98，
   同时把 embedding 的全部指标都推高（0.90 → 0.92，近问法 0.97 → **1.00**）。条件本身是量出来的——
   钉住*所有*逐字命中会让近问法掉到 0.88，因为那些问句复用了记忆自己的词，里面有很多"长得像名字"的普通词。

**"默认仍用词面检索"现在是一句有数字的话**：`embedding + 名字钉住` 在每一列上都不低于默认
（只有标识符 0.98 对 1.00，两者都基本满分）。它没成为默认，唯一的理由是它需要 provider、key、
以及把记忆发到那家 provider——不是因为它更差。

### 注入覆盖率的另一个分母：18 / 20 = 90%

漏斗里那 16 条被类型白名单挡住的目标（`fact`）**在线上根本不可能存在**：写入闸门的实测台账里有
`type-disabled:fact` 的 skip 行，这类句子写不进去。它们在语料里，是因为语料构造器用信号给记录定型
（`matchTypeSignals(text).type ?? 'fact'`），而不是重跑一遍闸门。

按"线上真的可能存在"的目标算，注入覆盖是 **18 / 20（90%）**，而排序漏掉的是 **0**。
所以 50% 这个分母的适用范围要说清楚：**"排序满分"是可迁移的结论，"50%"不是**——
它含了 16 条线上写不出来的句子。

## 下一步（按价值排序）

1. **补一批"精确标识符"探针**（文件名、报错码、环境变量、函数名）。现在的 36 条探针里一条都没有，而这正是词面检索的主场——不补，就没法判断 `searchRanking: embedding` 该不该成为默认值。
2. **自动注入那条路是最大的缺口：覆盖率 2/36**。它完全不看问题，每次会话开头按"重要度 + 时间衰减 + 类型配额"塞固定几条。要做的是让注入也看一眼当前回合在聊什么，然后按相关性挑——这是产品层面的改动，但 6% 这个数字说明它值得做。
3. **多相关标注**：现在的相关性口径是单目标（只有派生探针的那条算相关）。对每个探针人工判一下非目标的那几条（`recall1.csv` 里 `label` 留空的那些行），才能知道这个假设罚错了多少。
