# dsh-jev-memory

**类型化、可审计的 DSH 长期记忆插件。** 一句话定位：

> `AGENTS.md` 是人手写的记忆；这个插件是**自己长出来、按需召回、逐条可审计**的记忆。

DSH 官方有会话持久化（JSONL）、会话检索（SQLite FTS）、compaction（压缩丢弃），但**跨会话的长期记忆**是空白：没有任何官方包回答"什么值得记住"和"这一轮该想起什么"。本插件补的就是这一层判断。

---

## 它做什么（当前已实现并实测）

| 环节 | 实现 | 位置 |
|---|---|---|
| **写入** | 挂在 `agent/turn-stopping`（serial + awaited，回合收尾前）抽取候选 → 判定 → 过确定性闸门 → 落盘 | `dsh/index.ts` |
| **判定** | 端口式：**Jev**（TypeSafe 判定模型）为首选，**确定性信号**为离线兜底。判定层只出标签与概率，**不生成文本** | `dsh/lib/judge.ts`、`dsh/lib/jev.ts` |
| **存储** | 本地 `memory.json` + 只追加的 `ledger.jsonl`，原子写、内存索引（注入回调必须同步） | `dsh/lib/store.ts` |
| **召回** | `systemPrompt.context` 每步注入当前工作区的 Top-K，带类型/id/日期标签 | `dsh/lib/recall.ts` |
| **工具** | `memory_search` / `memory_write` / `memory_forget`，模型可主动查、主动记、主动撤 | `dsh/index.ts` |

三条纪律写进了代码，不是写在文档里：

1. **模型不写**——记忆正文只能是用户原话（逐字裁剪）或工具失败的确定性签名，判定层没有可以塞进新句子的字段；
2. **概率只排序，阈值归代码**——写入阈值是 `minImportance`，冲突判断用插件自己的 `conflictThreshold`，从不把 Noul 上调好的阈值搬到 Choice 上（官方 jaggedness 文档：P(q)+P(¬q) 未必等于 1）；
3. **fail-open**——判定失败降级到启发式，钩子超时直接放弃，写入路径的任何异常都被 catch，绝不让记忆成为会话失败的原因。

## 快速开始

### 方式一：开发期直接挂工作区（无需安装）

在 profile 的用户 patch 层 `~/.dsh/profiles/web/cordis.patch.yml` 里加一行：

```yaml
- insert:
    - id: jev-memory
      name: 'file:///absolute/path/to/dsh-jev-memory/dsh/index.ts'
```

行名由加载器用 `new URL(name, baseUrl)` 解析，所以 `file:` URL 与裸包名都可用。删掉这一行即完全卸载。

### 方式二：作为一个包安装进 profile

```sh
dsh plugin --profile web add /absolute/path/to/dsh-jev-memory
# 再把包名加进 profile package.json 的 dsh.profile.bundles
```

包根自带 `cordis.patch.yml`，`dsh.bundle.patch` 指向它。

### 配置

```yaml
- insert:
    - id: jev-memory
      name: 'file:///absolute/path/to/dsh-jev-memory/dsh/index.ts'
      config:
        types: [constraint, pitfall, decision]   # 只记这三类
        judge: auto                              # auto | jev | heuristic | off
        writeMode: pipeline                      # pipeline = 分段+抽取+判定+闸门；model = 一次调用全判（见下）
        minImportance: 0.6                       # 确定性写入阈值
        minRemember: 0.6                         # Jev 的"值得记吗"阈值
        askOnConflict: true                      # 发现矛盾时问你一句（HITL）
        askOnConflictTimeoutMs: 600000           # 等你回答的预算（10 分钟）
        askOnConflictMaxAttempts: 3              # 超时后在下一次对话开始前重问，最多几次
        repeatFailuresToWrite: 2                 # 同一个错重复几次才算"坑"
        writeSkipSubagents: true                 # 见下方"实测发现"
        writeTimeoutMs: 2500                     # 回合收尾的写入预算，超时放弃
        modelWrite:
          window: 10                             # model 模式下模型能读几条消息
          timeoutMs: 1500                        # 它自己的预算（会被上面那行夹住）
          retry: 1                               # 答案缺 JSON / 全被拒时重试几次
        recall:
          maxTokens: 600
          queryMessages: 3                        # 用最近几条你说的话当查询（0 = 关掉相关性排序）
          relevanceWeight: 0.8                    # 相关度 vs 重要度；见下方扫描表
          quota: { constraint: 4, pitfall: 3, decision: 2 }
          # types: [constraint, pitfall, decision, fact]   # 注入白名单，与写入白名单是两个决定
        jev:
          apiKeyEnv: TYPESAFE_API_KEY   # 从下面三处按序解析，密钥不写在配置里
          model: jev-latest             # 台账会记录实际应答的版本号，便于发现别名漂移
```

**密钥放哪**：按序解析 **①** 宿主 `ctx.credentials` 服务的 `apiKeyEnv` 引用（存 `~/.dsh/.credentials.yaml`，权限 0600）→ **②** 直接读同一个凭据文档（服务在开机那一瞬可能还没就绪，这条兜底让"时机"不再决定判定方式）→ **③** 配置里的 `apiKey` / 进程环境变量。解析发生在**每次判定时**而不是挂载时，所以运行中新增或轮换 key，下一轮就生效、不必重启。台账的 `start` 行写明实际用了哪条路径（`service:file` / `file` / `config` / `env` / `none`）。没有 key 时 `judge: auto` 自动退回启发式，**插件无需网络即可工作**。

## 记忆互相矛盾时：问你一句（人机协作）

"这条值不值得记"是一回事，"它是不是和你之前说的冲突"是另一回事——后者机器不该自己拍板：

1. Jev 若判**存在冲突**（概率 ≥ 0.7）**且这条本身值得记**，先以"待确认"状态落盘（不注入、也不丢）；
2. 回合结束时**问你一句**——一条问题、三个选项：**用新的覆盖旧的 / 保留旧的那条 / 两条都留着**；
3. 你的选择决定结果：覆盖 → 旧的标成"已被取代"（留档，不再注入）；保留旧 → 新的丢弃；都留 → 两条都生效；
4. **没人应答 / 超时（默认 10 分钟）/ 出错** → 保持"待确认"：**宁可少记一条，也不猜你的意思**。超时不是终点：记录留在"待确认"，**在你下一次发消息、模型开始干活之前再问一次**（那时的你一定在场），最多重问 3 次——这就是"超时敢设长"之所以安全的原因。

**为什么这和 DSH 原有的 HITL 不冲突**：DSH 有两种跟人打交道的通道——**审批**（沙箱/权限策略发起，"这个危险操作放不放行"）和**提问**（模型发起，"我缺一个信息"）。这里**复用第二种**，只是换成插件的判定规则来发起：不新增 UI、不新增权限模型、不新增打断渠道，问题会出现在你熟悉的那个提问卡片里。唯一的差别是"谁决定要问"。

台账会记 `conflict-ask`（问了什么、和哪条冲突、配对依据的共享词）与 `conflict-resolved`（你选了什么）——**这就是"自动判断靠不靠谱"的实测数据**。

**一次性失败不记**：工具报错要**同签名重复出现**（默认 2 次）才算"坑"。一次性的环境失败（沙箱拒绝、重定向被拦）不是教训；重复发生的才是。次数从台账里数，所以重启不丢。

## 实测发现：写入精确率 1/4（已修）

第一次在真实 GUI 里跑，台账 `ledger.jsonl` 立刻暴露了问题：

```json
{"kind":"write","type":"constraint","by":"heuristic","importance":0.96,
 "source":{"sessionId":"5883ea6a-…","seq":8,
 "quote":"调用 `memory_write`，参数：{\"text\": \"语言不要选 Java\", …} 3."},
 "signals":["/不要/u"]}
```

这些是**我写给 subagent 的任务指令**，被当成"硬约束"记了下来。根因不是阈值调错，而是：

> **在委派子会话里，`source.kind === 'user'` 的消息不是人类的话，是父代理的指令。**

核实方式是从磁盘读那条会话的 header：`{"delegationDepth":1,"agentPreset":"cordis"}` —— 确认是子会话。

修复分两层，都带回归测试（测试用例直接用上面这些真实句子）：

1. `writeSkipSubagents: true`（默认开）——深度 >0 的会话不再参与学习。子会话的回合对父会话的钩子同样可见，所以不丢信息；
2. `screenSentence()`——拒收**任务指令**（`按下面步骤`、`第 N 步`、`把…贴出来`、`不要改写` …）与**载荷**（`{"key":`、代码块）。刻意做窄：`不要改动 data/ 目录` 这类真约束必须活下来。

这条记录本身就是这个插件的价值主张：**误记是可以被逐条追责的**，因为每条记忆都带着来源会话、seq、原句和命中的信号。

### 写入侧改成两层：原文全留，闸门只决定"要不要注入"（2026-10-02）

参考腾讯 TencentDB-Agent-Memory 的 L0/L1 分层重写了写入路径（细节与源码引用见
[`docs/what-to-borrow.md`](docs/what-to-borrow.md)）。改动前它有**一道二元闸门**：过不了筛子和判定的句子
**直接丢弃**。代价是我们自己量出来的——标注集里 **122 行标"不该记"的句子，插件当时已经扔掉了**，
后来改问法、改阈值时**拿不回来**；判定是会错的，而一个不能重审的判定等于**换了个说法的删除**。

现在：

| 层 | 内容 | 谁写 | 能不能被注入 |
|---|---|---|---|
| **L0 原文归档**（`l0/YYYY-MM-DD.jsonl`） | 这一轮**每一条**消息，**包括助手自己发的** | 钩子同步写，不做判定 | 不进提示，但 `memory_search` **能搜到**，并标注"原文归档，未被采纳为记忆" |
| **记忆**（`memory.json`） | 通过闸门的记录 | 闸门通过后 | 进注入 |

两件事因此变得可能：一是**判定可重审**——改了阈值可以拿归档重跑，不用重新采会话；二是**"谁说的"检测有了证据**——
要判断"这句话是不是模型说的"，必须拿同会话里它更早说过的话来比，而在此之前**没有任何地方记录助手消息**。

**归档不是法外之地**：`memory_forget` 对归档 id 同样**真删**（重写当天文件，不是打墓碑）——搜得到却删不掉，
比没有记忆更糟。删除按"会话 + 序号"匹配，只按序号会把别的会话里同号的消息一起删掉。

**同时把 Jev 移出了写入闸门。** 实测（round5，140 行已定、18 条该记）：

| 判定 | 写对率 | 该记覆盖率 | F1 |
|---|---|---|---|
| **规则判定（现在线上）** | **26%** | 50% | **0.34** |
| Jev（新问法 + 阈值 0.12） | 24% | 50% | 0.33 |
| 并集 | 22% | 61% | 0.33 |
| 交集 | 30% | 39% | 0.34 |

不只是打平——**两者各自"独有贡献"的命中率一样低**：只有 Jev 说要写的 14 行里 2 行对，只有规则说要写的 12 行里
也是 2 行。花一次网络调用去追平一条本地规则不划算，所以配置默认变成 `writeGate: deterministic`。

**但 Jev 没有下岗**，它换到了它真正擅长的地方：它的 `remember` **排序**能力是 AUC 0.75（会排序），
而**拍板**能力是 F1 0.33（不会拍板）。所以它继续负责冲突/重复判定（`pairDecision`，决定"这是重复、是矛盾、还是新的"），
以及后续的检索相关度。`writeGate: judge` 保留着，万一将来某个模型把它挣回去。

### 写入覆盖率的天花板在哪：类型白名单（2026-10-02）

165 条已定行里，**102 条没有任何类型信号**，其中 **8 条是你标"该记"的**。它们会被闸门第一道检查直接拒掉
——`applyGate` 先看类型在不在 `{constraint, pitfall, decision}` 里，而 `matchTypeSignals` 没命中任何家族时
`type` 是 `null`，`heuristicRow` 兜底成 `fact`，白名单不含 `fact` → **拒，而且根本不看分数**。

类型信号是一张**关键词清单**，命中就是命中，没命中就是没有。所以"我**要求**是端口固定 8000"这种句子
——人一看就是硬约束——在清单里找不到任何一个词。

**两道闸其实来自同一次命中**：`candidateScore = 0.35 + matchTypeSignals(...).weight × 0.35 + …`，
所以往清单里加一个词，类型和分数会**一起**抬起来。

> ⚠️ **一处更正**：我先前的量法只从外部替换了类型查询，`candidateScore` 内部仍在用真清单，
> 于是得出"即使类型对了，分数那关还是过不去"。**那是量法造成的假象。** 真跑一遍：

| 规则 | 写对率 | 该记覆盖率 | F1 | TP / FP / FN |
|---|---|---|---|---|
| 现状 | 22% | 57% | 0.32 | 12 / 42 / 9 |
| + `应该\|应当\|请` 算约束 | 22% | 62% | 0.32 | 13 / 47 / 8 |
| + `我觉得\|我认为` 算约束 | **25%** | **67%** | **0.36** | 14 / 42 / 7 |
| + 五个一起 | 24% | **71%** | 0.36 | 15 / 47 / 6 |

所以**加词是能推动这个天花板的**（`我觉得|我认为` 这一版甚至没有多一个假阳性），
但它靠的是 **2 行**数据，而且 `我觉得` 在语义上根本不是约束信号——它标记的是"用户在表达看法"，
和"用户提了一条要求"是两回事，只是碰巧在这 2 行上重合。

**准确的说法**：确定性规则只认**祈使句式**的要求；你的要求里有相当一部分是**判断句式**的
（"我觉得…应该…不合理"），那要靠读得懂语义的东西来认。加词能捞回一部分，每加一个都在赌它别处不会变成假阳性。

### 句子边界交给模型：窗口 5 条，归属决定谁能成为记忆（2026-10-02）

确定性切句是**按标点**切的，我们把它和你的标注对过：note 说"切得不好"的 16 行里，**12 行是机械问题**
（240 字截断、尾部序号、代码行——都修了），剩下 4 行**不是机械问题**：它们是**一条消息里混了你自己的话和
你粘贴的模型输出**。这没有标点规则能分开，而你的 note 说得很直白——"末尾这段是我复制的模型的输出，
后面应该才是我要补充的点"。

所以写入路径上多了一步：模型读**最近 5 条消息的窗口**，只回答两件事——**边界在哪、每段是谁写的**
（`user` / `quoted` / `pasted` / `tool-output` / `assistant`）。只有标成 `user` 的片段会成为候选；
标成 `pasted` 的原文**仍然进归档、仍然可搜**，但不会当成你的主张被记住。

**两条安全性是强制的**（`dsh/lib/segment.ts`）：

1. **模型返回原文、不返回下标**，位置由我们在消息里搜出来——所以它**没法改写、翻译、编造**；哪段不是逐字出现，整份答案作废。
2. **覆盖率过低的答案作废**，不做修补。模型漏掉半条消息却算成功，正是这个项目一直拒绝的静默失败。

**第三条是后补的，因为第一版漏了它**：模型**答过的消息，它的话就是权威**——包括"这条消息里没有你的话"。
原来的判断是"这条消息有没有 `user` 片段"，没有就退回标点切句，于是**归属只对"混着你的话的消息"生效**：
一整条都是粘贴块的消息会绕回切句，粘贴内容照样能被记成你的要求。只有整条全粘贴时才走得到，所以前面那个
"混着粘贴块"的测试没抓到它。2026-10-03 修掉，并加了一个反向对照的测试（同一句话：模型说过 → 不记；
没有模型参与 → 本地规则照记）。调用**失败/超时/被拒**时传的是 `null` 而不是 `[]`，切句仍然拥有那些情况。

**每一条失败路径都退回原来的行为**：没有 `llm` 服务、没有路由、答案被拒、写入预算内超时——全部回退到标点切句。
每轮台账写一行 `segment`（成功与否、原因、几段、几段是你的、几段是粘贴的、覆盖率），
**所以超时率是量出来的而不是猜的**——这个调用在 2500ms 的钩子预算里，如果经常超时，正确的做法是把它挪到后台，不是把预算调大。

> 实测（`eval/judge-context.ts`，90 条还原出窗口的标注行）：**给窗口让判定层的 AUC 从 0.69 升到 0.73–0.76**，
> 但阈值上的取舍没明显变好——D 版短问法让正例更自信（中位分 0.29 vs 0.27），也多放行了负例（41/72 vs 33/72）。
> 结论：**窗口值得给，但它本身不足以把 Jev 请回写入闸门。**

### 修掉一个我自己引入的严重 bug：`writeGate: deterministic` 名不副实

它的第一版实现是"把 `remember` 拿掉"，于是 `applyGate` 退回读**判定层自己的 `importance`**（0–1 的 score 答案）对 0.6。
**这个组合我从来没量过**，而我当初的论据（F1 0.34 对 0.33）量的是**抽取器自己的类型和分数**。

量了之后：90 条还原出窗口的标注行里，正例 importance ≥ 0.6 的**不带窗口 2/18、带窗口 0/18**——
**线上闸门几乎是焊死的**，而且台账上看不出来，因为"闸门关着"和"这一轮没什么可记"长得一模一样。

现在 `deterministic` 真的用**本地的类型和分数**（判定层的 `conflict` 仍然保留，冲突复核依赖它）。
两个测试钉住两个方向：模型对所有问题都答"不"，也拦不住本地规则接受的句子；模型对所有问题都答"是"，
也放不进本地规则无法定型的句子。

### 第二条写入路径：一次调用全判（`writeMode: 'model'`，2026-10-03）

你要求"写入侧用模型结合最近五条消息做语义拆分"，又问"换提示词、给足上下文多测测，指标会不会好转"。**先量再写**，
在 120 条还能还原出窗口的标注行上（同一批行、同一个窗口、同一个模型、同一套标注）：

| | 精确率 | 召回率 | F1 | TP / FP / FN |
|---|---|---|---|---|
| **一次调用**（新路径） | **56%** | **90%** | **0.69** | 18 / 14 / 2 |
| 现在的流水线（分段 → 抽取 → 判定 → 闸门） | 27% | 60% | 0.37 | 12 / 32 / 8 |

**两个方向同时变好**，这就是新开一条路径而不是继续调流水线的理由。注意差别不在"有模型参与"——判定层早就有模型，
F1 0.33，和免模型的规则打平。差别是这次它**看得见窗口**、拿到了你那条判断标准，而且回答的是一个**有界问题**
（每段：值不值得记 + 是哪种记忆），不是给一句孤立的话打分。

**它能做的**：读最近 10 条消息，逐段返回 `{message, text, who, worth, type}`，`text` **必须逐字**
（`dsh/lib/modelwrite.ts`）——**不返回下标**，位置由我们在消息里 `indexOf` 搜出来，搜不到就整项作废。
这条规则是"先量出来的"而不是"保险起见加的"：同一套思路**不要求逐字**时，F1 只有 0.37（和流水线打平），
而且 **22% 的返回不是任何人的原话**，其中一处把"集成"写成了"继承"——**结论被改了**，还挂在你名下。所以这里只留提议，不留文风。

**它不能做的**（这些故意没被绕过）：

- **确定性筛句仍然先跑**：密钥、粘贴块、任务指令、代码片段、提问照样被拒。这里要说清楚，**0.69 和筛句的成绩不能相加**——
  那 120 条标注行本身就是筛句活下来的行，筛句在更早的池子上交出的是 19% / 100%。
- **模型回声筛仍然跑**：模型自己说过、你又粘回来的句子不是你的要求。
- **重复/矛盾判定仍然问判定层**：这是另一个问题（这段文字 vs 库里已存的那条），用的是它的排序能力（AUC 0.75）。
  所以 **Jev 在写入侧现在只剩这一件事**——不在闸门里，也不定型（类型由这次调用给）。
- **它答过的消息归它管**：`[]`（"没有值得记的"）是决定，不是"没回答"。这点第一版写错了（见上一节第三条），
  错法是空的答案会退回本地规则、把刚被它否掉的句子又写进去——**那就不再是我量过的那个规则了**，
  而 README 上的 0.69 说的是量过的那个。

被跳过的只有**本地的类型+分数闸门**（`applyModelGate`）：标注里 21 条正例有 **8 条**死在类型白名单上，
原因是关键词——`顺便我觉得这个配置流程应该再简化一下。` 因为"流程"被判成 `procedure`，而 `procedure` 不是记忆类型。
那是撞运气，不是理解，让一次看得见上下文的调用去否决它才是对的。测试把这个对照钉住了：**同一句话，
`pipeline` 下被拒且台账写明 `type-disabled:procedure`，`model` 下被记成 `constraint` 并出现在检索里。**

**代价我量了，而且是这条路径默认关闭的原因**：

| | 中位 | 最慢 | 超预算 |
|---|---|---|---|
| 分段调用（现在线上） | 851ms | 1271ms | 1/11 |
| **一次调用** | **1233ms** | **3701ms** | **16/49（33%）** |

最慢那一次**比整个 2500ms 写入预算还长**。所以：

1. **默认 `writeMode: 'pipeline'`**，要开就显式开一行配置。它每轮多花一次模型调用，而延迟贴着预算。
2. **失败时不追问分段**。超时/答案被拒就退回**标点切句 + 本地闸门**——那是一次更慢的决定，不是丢掉的一轮。
   如果失败后再调一次分段，两次网络往返必然撑爆预算，**整轮写入归零**，那才是真的损失。
3. 每轮写一行 `write-path`（模式、窗口、模型、`items` / `worth` / `kept`、失败原因）。
   `reason` 是 `ok` / `unparsable` / `all-refused` / 超时；**`worth - kept` 就是类型白名单还在拒的值不值得记的句子**。
   如果 `ok` 占比长期偏低，该动的是**把它挪到后台**，不是把预算调大。

### 召回侧：注入现在看一眼当前对话（2026-10-03）

读取侧最大的数字一直是**自动注入覆盖率 2/36（6%）**：注入完全不看问题，按"重要度 ×0.85 + 时间衰减 ×0.15 + 类型配额"塞固定几条，
于是"库里有没有"和"进没进提示"之间没有任何关系。

改法是把**这个人最近 3 条消息**当作查询，与重要度加权混合（`recall.queryMessages` / `recall.relevanceWeight`）。
用同一批 36 个探针扫权重：

| 相关性权重 | 覆盖率 | 注入里真记忆占比 |
|---|---|---|
| 0（原来） | 0 / 36 | — |
| 0.35 | 16 / 36 | 22% |
| 0.5 | 16 / 36 | 30% |
| **0.8（默认）** | **17 / 36** | **42%** |
| 1.0 | 16 / 36 | 39% |

覆盖率和"注入进去的是真记忆的比例"在 0.8 同时到顶，**不是拿一个换另一个**——因为旧排序是被
"看起来重要"塞满的，而库里看起来重要的记录大多是写入侧的假阳性（冻结语料 94 条里 76 条）。

**顺带修掉一个预算 bug**：注入块只算了记忆行、没算标题和撤销提示，实测 **641 token 对 600 预算**——报了个预算又超了它。

**预算这个旋钮量过，结论是别动**：600 → 1200 是每轮多花约 580 token，只多换 1 个探针（17→18/36）。

**"刚写进来的"也单独量了**（冻结语料没有时间，所以是明确标注的模拟：给每个探针追加一条"刚写的"记录）。
两种机制——**预留槽位**（硬保证）和**新近加成**（软竞争）：

| 机制 | 刚写的真记忆被注入 | 覆盖率 |
|---|---|---|
| 不开 | 9 / 36 | 17 / 36 |
| 预留槽位 1 | 29 / 36 | **16 / 36** |
| **新近加成 0.4（上线）** | **32 / 36** | **17 / 36** |
| 新近加成 0.6 | 36 / 36 | 16 / 36 |

**软竞争严格优于硬保证**：0.4 到手 32/36 而覆盖率一点没掉；预留槽位要拿覆盖率换（它挤掉的正是排名最低的那条）。
0.6 能到 36/36 但掉 1 个覆盖率探针，说明它开始滑回硬保证区间，所以不取。
代价那列两种机制一样高——都只看时间不看内容，而写入侧精确率 24%，"刚写的"四分之三是垃圾。

**47% 之后不再涨，瓶颈不在排序**。把"在库里→进提示"的三道闸门分开量：类型白名单卡掉 **16 条**、
token 预算卡掉 3 条、类型配额 0 条、**相关性没排进 0 条**。这 16 条被标成 `fact`，
而线上库里**一条 `fact` 都没有**（核对过：16 条全是 constraint / decision / pitfall）——
因为写入侧的同一座白名单在写的时候就已经把它拒了。

顺带把两座白名单**拆成两个配置值**（`types` 管写入、`recall.types` 管注入），因为它们本来是两件事，
而且合在一起时根本问不出"放行 `fact` 能换到什么"。拆开后量出来的上限是：

| 注入白名单 | 配额 | 覆盖率 | 每轮 token |
|---|---|---|---|
| constraint / pitfall / decision（今天） | 4 / 3 / 2 | 17 / 36（47%） | 592 |
| 再加 `fact` | 再加 fact 4 | **28 / 36（78%）** | 593 |
| 再加 `fact` | 再加 fact 8 | 27 / 36（75%） | 593 |

**78% 是上限而不是开关**：线上没有 `fact` 记录，所以只改注入**今天没有任何效果**；要真拿到这 11 个探针，
得先决定**写入侧写不写**这类没有类型关键词的句子——那是那个有标注依据的决定（写入侧已知
"21 条正例里 8 条死在白名单上"），而且要连带决定"用什么类型存"。同样注意配额不是越大越好
（fact 4 → 28，fact 8 → 27：同一条预算下，放进更多 `fact` 会挤掉分数更低的其它类型）。

还有一个坑值得记：**只放宽白名单是不生效的**，因为配额表里没有 `fact` 这一项时，`quota[type] ?? 0` 会把它拒掉——
两个闸门都得开。测试把这个"看起来没用的旋钮"钉住了。

**这一步踩到两个"功能看起来在工作、其实完全没生效"的坑**，都由测试抓出来，记下来免得重犯：
1. 相关性打分忘了传 `cwd`，而 `searchMemories` 按 `cwd` 过滤——工作区内的记忆全部得 0 分，
   相关度那一项静默失效，排序看起来仍然正常（那是旧分数）。
2. `session.eventAt()` 返回的事件没有 `seq`，而 `archiveMessages` 只认带 `seq` 的事件——
   查询永远是空串。**库级测试抓不到它，因为坏的不是库，是接线**；端到端测试才抓到。

### 线上从未成功过的两个调用：思考 token 吃掉了输出预算（2026-10-03）

准备打开 `writeMode: 'model'` 时先去翻线上台账，发现两件事**不是"效果好不好"，而是"从来没成功过"**：

- `segment` 行 **5 条全是 `ok: false, reason: 'unparsable'`**；
- `normalize` 行 **12 条里 9 条 `empty`、1 条 `refused`、2 条 `unchanged`，`ok` 一次都没有**。

`unparsable` 和 `empty` 这两个词都指向"提示词写得不好"，所以先照着提示词查——**查错了**。用同一批真实窗口、
同一套提示词直接打线上的路由（`deepseek-flash`），才看到真正的原因：**这是个会思考的模型，而思考 token 和正文
token 共用一个 `max_tokens`**。用返回里我原来丢掉的两个字段（`finish_reason`、`reasoning_content`）看得很清楚：

| 调用 | 预算 | finish_reason | 思考字符 | 正文字符 | 结果 |
|---|---|---|---|---|---|
| 规范化形状 | 400 | **length** | 694 | **0** | 整个预算花在思考上，一个字没输出 |
| 分段（2 条消息） | 1200 | stop | 599 | 151 | 通过 |
| **分段（真实 5 条窗口）** | 1200 | **length** | 356 | 1621 | **JSON 被从中间切断 → `unparsable`** |
| 分段（真实窗口，预算加大） | 3000 | **length** | **3000** | **0** | **更糟**：思考把钱花光，12.5 秒 |

**加大预算只会让它想得更久**，这是反直觉但量出来的部分。真正的开关是**这一轮不要思考**——
DSH 自己就是这么干的（它的会话标题调用用 `purpose: 'session-title'` 强制关掉思考），
适配层也写明 `reasoningEffort: 'off'` 永远合法。所以在同一批窗口上量了开/关两种：

| 调用 | 开着思考 | 关掉思考 |
|---|---|---|
| 分段（6 个真实窗口，两次运行） | **2/6、2/6 通过**，中位 4467 / 5996ms，最慢 11690ms | **4/6、4/6 通过**，中位 860 / 824ms，最慢 5061ms |
| 规范化（4 句话，两次运行） | 3/4 有输出，中位 1878–2026ms | **4/4 有输出**，中位 638–730ms，最慢 1215ms |
| 一次写入调用（6–7 个真实窗口） | 0–1 条可写，中位 **3623 / 6614ms**，**2/6–7 被截断** | 1–2 条可写，中位 **596 / 686ms**，**0 被截断** |

（表里给两次运行的区间而不是一个数：`eval/thinking-budget.ts` 可以重跑，
两次的中位数差 10–15%，**中位可复现、尾部不可复现**——关掉思考后分段仍有单个窗口跑到 5061ms，
所以预算不够时该做的是让它异步，而不是把 `budgetMs` 往上调。）

所以三个调用（分段、规范化、一次写入）现在都带 `reasoningEffort: 'off'`，
并且**把 `finish_reason` 读出来了**：预算耗尽导致的失败现在叫 `truncated`，不再和"答案读不懂"共用一个词。
`start` 行也记下 `thinking: 'off'` 与分段预算，好让"改了之后数字有没有变"这个问题在台账里能回答。

复现方式：`DSH_LIVE_ROUTE=yes LIVE_LIMIT=6 node eval/thinking-budget.ts`（约 40 次真实调用，会花钱）。

**还有一个必须说清楚的缺口**：一次写入调用的 **0.69 是在 `deepseek-chat` 上用原始 HTTP 量的**（不思考），
而线上路由是 `deepseek-flash`。在真实窗口上它现在能被解析、能在预算内返回（中位 596ms），
但**它在这条路由上的准确率还没有量过**——所以 `writeMode` 仍然默认 `pipeline`，
而且上面那个 0.69 不该被读成"线上就是这个数"。另外 7 个真实窗口里有 **5 个它答的是 `[]`**；
这些窗口里你的话大多是"实现一下吧"这类一次性指令，答 `[]` 很可能是对的，
但这恰恰说明**要判断这条路径的召回，得先有一批以你的话为锚点的窗口**，不是拿这条数据下结论。

### 读取侧：记忆在需要的时候能不能被想起来（2026-10-01）

写入侧回答"记不记得住"，读取侧回答"用不用得上"。**这一侧以前一个数字都没有**，项目叫"长期记忆"却只量了一半。现在有了：

```
node eval/harvest-queries.ts     # 从你标"该记"的句子造探针（每个 2 个：近问法 / 远问法）
node eval/recall-report.ts       # 算 Hit@K / MRR / 注入覆盖率；RECALL_BASELINE_OUT=... 冻结基线
```

第一版：**36 个探针**（18 条真记忆 × 2），库 **94 条**（18 条真记忆 + 76 条闸门会写进去的垃圾，**垃圾占 81%**——这不是编的，是写入侧精确率 24% 的另一面）。

| 检索方式 | 近+远 Hit@1 | 近+远 MRR | 标识符 Hit@1 | 标识符 MRR |
|---|---|---|---|---|
| 旧版子串匹配 | 22% | 0.23 | 95% | 0.97 |
| embedding（512 维） | 86% | 0.90 | **0%** | **0.00** |
| 纯 BM25（改到一半时的样子） | 67% | 0.71 | **0%** | 0.31 |
| **BM25 + 名字精确命中加成（已上线）** | **67%** | **0.71** | **100%** | **1.00** |

四件事，第 3 件是我自己踩的坑：

1. **子串匹配不该用来检索散文。** `memory_search` 原来是"整串出现 +1、分词出现 +0.3"的包含判断，远问法 18 条里 **17 条什么都返回不了**——而"换个会话换种说法再问一次"是最正常的用法。换成 BM25 是**零新增依赖**的改动：BM25 的代码本来就在项目里，一直只给冲突排序用，检索这条路从没接上。MRR 0.23 → 0.71。
2. **embedding 在散文上更强，而且是"换掉"而不是"融合"。** 逐条比过：Hit@5 内两边都中 27 条，**只有 embedding 中的 7 条，只有 BM25 中的 0 条**。朴素融合反而更差（0.74 < 0.90），因为 BM25 对自己的第一名永远给 1.0 分，一个自信但错误的词面命中会压过语义命中；RRF 只找回一部分（0.83）。所以做成一个模式开关 `searchRanking: lexical | embedding`，**默认 lexical**——embedding 会把查询和库里每一句都发给服务商，这个不能让默认值替人决定。
3. **换成 BM25 把"查一个具体名字"这类查询弄坏了，是我先漏掉的一类。** 补了一组机械生成的标识符探针（`memory.json`、`KnowledgeBase._load_default_docs` 这种只出现在一条记忆里的名字）才发现：**旧子串匹配在这类查询上是 Hit@1 95% / MRR 0.97，纯 BM25 只有 0% / 0.31，embedding 是 0% / 0.00**。原因是标识符在 BM25 眼里只是一个词，而 `memory`、`json` 这种词 IDF 很低。修法不是"融合两个排序器"，而是**在分数里加精确命中加成**：查询里出现的名字只要在原文里逐字命中就加分。权重扫过一遍：加成 ≥12 时标识符 MRR 到 1.00，而散文那 36 个探针**在 0 到 128 之间一点没动**（都是 0.71 / 67%），取 16。现在标识符 100% / 1.00，比被我替换掉的旧实现还好。
4. **自动注入那条路不看问题，覆盖率只有 2/36（6%）。** 它按"重要度 ×0.85 + 时间衰减 ×0.15"加类型配额挑，跟你在问什么无关。这是目前最大的产品缺口，写在 `docs/reading-side-baseline.md` 的"下一步"里。

**局限（写在报告里，不藏着）**：相关性是**单目标**口径——只有派生探针的那条记忆算相关，两条都能回答同一问题时第二条会被算成噪音。标识符探针的目标既可能是真记忆也可能是垃圾行（这一组量的是"词面能不能对上"，不是记忆质量）。32 个散文探针也是我自己出的题，不是真人查询日志——真实意图比这更难。

### 写入精确率是怎么量的

`eval/write-precision.ts` 是一套**带标注的候选集**（20 条 = 8 条该记 + 12 条不该记），其中 8 条"不该记"取自真实会话里插件**确实写过**的原句（子代理任务指令、一次性环境失败、用户提问、API key 本身）。

**它只有 20 条，只能证明"没有明显坏掉"，不能当结论用。** 真实分布的量法在 `eval/labels/`：从历史会话里抽出候选句、由人逐句标注，再对照三种判定（只过筛子 / 规则判定 / Jev）。那份数据的抽样口径和批次说明写在 [`eval/labels/README.md`](eval/labels/README.md)，逐句结果在 `eval/labels/report.md`（`node eval/report.ts` 生成）。

这个"身份取自原句、其余取自清洗文本"的错位很容易写反，我第一版就写反了（注释说原句、代码传了清洗后的），**是测试抓出来的**，现在有测试钉住。

### 两层记忆：原句是证据，规范形式只用于注入（2026-09-29）

之前存的是**你原封不动的那句话**。好处是"绝不编造"——记忆永远能追回到一句你真的说过的话；坏处也真实：错别字、口水话、断句会一起进上下文。别家都改写（memsearch 把每回合变成 2–10 条第三人称 bullet，OpenViking 抽进带 `as of` 日期的类型化文件），**照搬原句的才是异类**。

所以现在是两层，分开的理由就是这张表：

| | 内容 | 谁写 | 用途 |
|---|---|---|---|
| **证据层** | 你原句，**永不被模型改写** | 你 | 台账、`source.quote`、逐条核对 |
| **规范层**（新增字段 `canonical`） | 模型整理过的第三人称陈述 | 模型，受硬约束 | **注入**（默认不启用） |

三道闸门防止它变成编造通道：

1. **不许添加事实** —— prompt 明说，并且有**确定性闸门**兜底：规范形式的词元里必须有足够比例来自原句。阈值不是拍的，是量出来的：把「嗯那个啥 就是 端口别乱改啊 定了 8000」整理成「服务端口固定为 8000，不要修改。」共享 **0.375** 的词元，而一句**编造了理由和后续动作**的扩写只共享 **0.19**，阈值取 **0.25**。判错的方向是刻意选的：拒了只损失可读性，收了就把编造的内容送进上下文。
2. **不许静默接受** —— 过不了闸门**不修补、不裁剪**，直接丢掉、保留原句。fail-open 在这里的含义是"保留原话"，不是"保留模型猜的"。
3. **没有路由就不做** —— Jev 根本做不了这件事（它只能回答 `noul/choice/score`，**输出不了文本**），所以走**宿主自己的 `llm` 服务**，路由取自 `agentDefaultModel.currentSelection()`，也可以配置覆盖。没有路由就什么都不做，并且**只在挂载时报告一次**（`start` 台账行的 `normalize` 字段），不会每写一条就留一行失败噪音。

配置与默认值：

```yaml
config:
  normalize:
    enabled: true    # 生成规范形式（默认开）
    inject: false    # 注入时用它替换原句（默认关 —— 这会改变模型看到的内容，先看样例）
    # provider / model 留空 = 用宿主的默认模型
```

**默认不注入**，因为这一步改变的是**模型看到什么**。想看样例再决定的话，台账里的 `kind:"normalize"` 行就带着 `from` / `to`（各 160 字）—— 打开 `enabled` 跑几天，读那些行，满意了再把 `inject` 打开。

### 冲突窗口的排序：默认 BM25，可选 embedding（2026-09-29）

冲突确认那一步**不会把全部记忆丢给模型**——只给 `knownForConflict` 条（默认 20）。原来这 20 条是"存储顺序的前 20 条"，于是排在第二十一条的矛盾**永远不会被看到**，模型回答"不冲突"，台账里什么都不留。现在改成**按相关性排序**，打分函数是可替换的接口：

| `conflictRanking` | 实现 | 依赖 | 代价 |
|---|---|---|---|
| `lexical`（默认） | 对记忆做 BM25 | 无 | 无，且**没有任何内容离开本机** |
| `embedding` | 余弦相似度（智谱 `embedding-3`） | 一个 key | 记忆正文会发给该服务商；派生向量缓存在 `embeddings.json` |

**BM25 用在这里合理吗？合理，而且中文分词的问题已经解决了 —— 不需要任何依赖。** 我原来写"中文没有分词器"，这个说法是错的：`Intl.Segmenter` 是 V8 自带的，Node 又是完整 ICU，**中文词典分词本来就在机器上**。

实测（查询 `端口不要用 9000 了`，正确结果应是"服务端口用 8000"排在"不要用 yarn"前面）：

| 分词方案 | 不要用 yarn | 服务端口用 8000 | 结论 |
|---|---|---|---|
| 全量字符 bigram（原来） | 2.733 | 2.188 | ❌ 排错 |
| **`Intl.Segmenter` 词元（现在）** | 1.814 | **4.959** | ✅ 正确 |
| 分词器词元 + 词内 bigram | 1.814 | 4.959 | ✅ 正确（与上等价，取更简单的） |

bigram 输的原因是 `不要用` 被切成 `不要` + `要用`，而 `要用` 成了罕见词、凭空制造 IDF；分词器在 `不要|用` 处切开，这个假词就不存在了。代码里还加了**运行时自检**：精简 ICU 的构建会把中文切成单字（比 bigram 更差），所以加载时用一句话探测，不通过就退回 bigram。

BM25 真正修不了的是**改写**（`data 下的文件别碰` ↔ `不要改动 data/ 目录` 只共享一个词），那是下面 `embedding` 开关存在的理由。

**embedding 修的是另一种情况：改写。** 实测（真实 API 调用，2026-09-29）：

| 对比 | 余弦 |
|---|---|
| `不要改动 data/ 目录下的任何文件。` ↔ `data 下的文件别碰`（改写） | **0.769** |
| `不要改动 data/ 目录下的任何文件。` ↔ `服务端口固定 8000`（无关） | 0.532 |

无关句也有 0.53 —— 所以**它只能用来排序候选，不能当绝对阈值**：真正区分的是相对顺序。另一方面 3 条文本一次请求 305ms、0.5 元/百万 token（全库约 3 万 token ≈ 0.015 元），缓存命中后不再请求。BM25 对这一对改写的得分接近 0，这也是为什么这个开关值得存在。

失败一律回退到 BM25（无 key、超时、报错、维度不一致），因为**排序是优化，写入不能依赖它**。

```
Jev @0.5   precision=0.88 recall=0.88 F1=0.88
Jev @0.6   precision=1.00 recall=0.75 F1=0.86    ← 默认阈值（同一次跑的另一次运行给 0.86，见下）
Jev @0.7   precision=1.00 recall=0.63 F1=0.77
```

**两个必须一起读的事实**（否则上面这张表会误导）：

1. **模型判定不是确定性的。** 同一批输入重复跑 10 次，16 条候选里 **15 条的分数都在变**（最大波动 0.07），其中 **1 条的分数在 0.54–0.60 之间反复越过阈值**——单次运行会让精确率在 **0.86 和 1.00** 之间跳。所以 Jev 的数字必须报重复跑的区间，单次结果不能当结论。
2. **默认阈值 0.6 会稳定地漏掉中文项目约束。** `不要改动 data/ 目录下的任何文件`（硬约束，标注为"该记"）10 次跑下来是 **0.50–0.53**，`sqlite 写入失败：EDQUOT…`（可复现的坑）是 **0.34–0.41**——两条都稳定低于阈值。这不是噪声，是召回损失：@0.6 的召回 0.75 就是漏了这两条。

写进台账的判定分（`remember`）现在也可以直接从台账复核：`kind:"remember"` 记录里带 `by` 和 `model`，能看出某条记忆是 Jev 判的还是启发式判的。

默认取 `0.6` 而不是 F1 更高的 `0.3`：**假阳性比假阴性贵**——一条错记会进入此后每一个会话的提示。两个已知漏判也写在这里：`不要改动 data/ 目录下的任何文件。`（Jev 给 0.51，恰好压线）与 `sqlite 写入失败：EDQUOT...`（给 0.38——只看到一次，无从判断会不会复现；这条已由确定性规则补上：同签名重复 ≥ `repeatFailuresToWrite` 次才落盘）。

> **为什么分开写 Hit@K 和 Recall@K**：多正例下两者会分叉（Hit@5=1 时 Recall@5 可能只有 1/3），只写"Top-3 命中"是不可复现的。这个教训来自 `zilliztech/memsearch` 公开的中英检索评测——它同时发布了两套定义，参见 `docs/memsearch-notes.md`。
>
> 指标分工也定了：**Jev 只用在写入判定，不用做召回重排**。memsearch 的公开评测里 Jev 作为 reranker 输给 Voyage rerank-3（Recall@5 0.7941 vs 0.8187、MRR@10 0.6884 vs 0.7754），作者据此拒绝把 Jev 设为默认——那是"给已有候选排序"这个位置上的负结果，和我们"写入判定"不是同一个任务，但**任何对外表述都必须承认这条公开数据**。

---

- **两种投递方式**：正常情况下走系统提示里的运行时上下文（便宜、稳定）；检测到 preset 关掉了运行时上下文时，改走一条**带插件来源的消息**（`form: "recall"`），并在台账记 `context-suppressed`。这条兜底是必需的：那种情况下宿主的装配器**根本不会调用我们的回调**，插件既不报错也不留痕——完全静默。

## 明确不做（避免和生态重复）

- **不做 UI / 面板**、不做向量库（类型化 + 少量记录不需要）；
- **不做**"从反复失败里长规则"（那是 `dsh-jev-forge` 的题目）、**不做**全量写入的人工分诊——只在你和旧记忆真的矛盾时才打扰你（见上一节）；
- **不碰 `dsh-jev-tools` 已覆盖的四个节点**：工具输出精简、注入筛查、技能推荐、交付闸门；
- 不与 `AGENTS.md` 争优先级：**人工手写 > 自动记忆**；冲突条目先落 `needs-review` 且默认不注入，再由你决定归属。

## 测试与验证

```sh
node --test test/*.test.ts      # 80 条，全离线，不联网、不启动 harness
pnpm run typecheck              # tsc --noEmit，零依赖包也能有真类型检查
```

包含一条完整的端到端闭环（用假 ctx 驱动真实代码）：写入 → 下一会话召回 → `memory_search` → `memory_forget`。

**为什么是 TypeScript 而不用构建**：Node 22.23 默认开启类型擦除（`process.features.typescript === 'strip'`），所以 `import('./dsh/index.ts')` 与 `node --test test/*.test.ts` 都能直接跑，**没有构建步骤，也就保住了"零运行时依赖 + 可被 `file:` URL 直接挂载"这个性质**。代价是只能用可擦除语法（无 enum / namespace / 参数属性 / 装饰器），相对导入必须写显式 `.ts` 扩展名。类型检查靠 devDependency 里的 `typescript`（与运行时无关）。

真实 harness 验证已做过一次（记录在 `docs/DESIGN.md` 的"实测记录"一节）：插件热挂进正在运行的 web profile，台账出现 `start`，一次子会话回合触发了 4 条写入，下一轮模型请求的系统提示里出现了 `## 长期记忆` 区块。

## 现状与未验证项（不编造）

- 离线全绿、真实进程内闭环已验证；
- **Jev 线上路径已用真实 key 跑通**：`POST https://api.typesafe.ai/v1/systemone` → `jev-1.13.0`，`docs/jev-api.md` 里的请求/响应结构逐字段对上（含 `answers.<id>.noul / .choice / .score / .confidence`）。**延迟量级 0.56–0.68s，但那是一次判 16 条、把上限临时调到 50 测出来的；默认上限是 6 条**（第 7 条起退回启发式，现在会记 `kind:"degraded"` 并告警）；
- **live 判定已确认走 Jev**（2026-09-28 重启后核实）：台账 `start` 行写着 `"version":"0.6.0"`、`"jev":{"ready":true,"source":"service:file"}`，且此后的写入/跳过记录都带 `"by":"jev"`、`"model":"jev-1.13.0"`。凭据走两条路（宿主凭据服务优先、直读凭据文档兜底），所以"服务在开机那一瞬还没就绪"不再决定判定方式；
- 多进程同时写同一个 `memory.json` 是 last-write-wins，单进程是受支持场景（TODO：锁文件）；
- **代码改动必须重启 harness**：Cordis 的 HMR 能重挂载插件行、重读存储，但 ESM 缓存不会重新求值 `lib/*.ts`。这条是**实测**的，不是推测：一次语义变更触发的重挂载后，`start` 台账仍写着旧 `version`、也没有新字段。`start.version` 就是用来判断"跑的是哪份代码"的；换一个**文件路径**（如 `.js` → `.ts`）会强制换一套模块 URL，那是唯一不用重启的刷新方式；
- 同机还有一个同类插件 `@zilliz/memsearch-dsh`（见 `docs/memsearch-notes.md`）：它与本插件**正交**，但挂在同一 patch 层，**同 profile 共存未实测**（可能双份注入）。
